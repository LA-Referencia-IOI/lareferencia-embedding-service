# Phase 10: streaming document and vector imports

Enable v2 and explicitly enable imports with `DVP_IMPORT_ENABLED=true` on the API and worker processes. Run at least one process with `DVP_WORKERS_ENABLED=true` and role `WORKER` or `ALL`. The tracked standalone configuration currently defaults imports to enabled; Compose and the example configuration default them to disabled. Set `DVP_IMPORT_ENABLED` explicitly for each process. Set `DVP_IMPORT_FILE_ROOT` to the same durable directory on all API and worker replicas. The volume must support atomic same-filesystem rename, directory fsync and cross-process advisory file locks. Verify these guarantees on the actual shared filesystem before deployment. The Compose `import-data` volume is local to its Docker host; use a shared volume for multi-host deployments.

Submit uncompressed UTF-8 JSON or JSONL using multipart form data:

```bash
curl -X POST 'http://localhost:8989/api/v2/collections/COLLECTION_UUID/imports' \
  -H 'Idempotency-Key: import-exemplo-001' \
  -F 'options={"format":"jsonl","mode":"merge"};type=application/json' \
  -F 'file=@docs/examples/import-records.jsonl;type=application/octet-stream'
```

`options` is required and contains only `format` (`json` or `jsonl`) and `mode` (`merge` or `replace`). `merge` follows PATCH semantics; `replace` follows PUT semantics for documents in the file and does not delete other documents. A 202 response contains a job ID and a `/api/v2/jobs/{job_id}` Location. Poll the job and its `/errors` route as described in [jobs operations](phases-5-7-persistent-jobs.md). The same idempotency key, normalized options, and original file bytes replay the original response. Different content with the same key returns 409.

JSONL contains one object per nonempty line, each with `schema_version: "1"`. JSON contains a top-level `schema_version: "1"` and a `documents` array; its records inherit the version. Both formats accept a leading UTF-8 BOM, which remains part of the file hash. Records are processed in file order, including repeated external IDs. JSONL syntax errors are recorded per line and processing continues. A malformed global JSON container fails the job with `file_correction_required` while preserving records already committed. If the JSON schema version occurs after the documents array, the container is preflighted before writes so that an unsupported version cannot be applied; malformed input detected during that preflight has no committed records.

The default file limit is 10 GiB (`app.dvp.max-file-bytes`); the per-record limit is 16 MiB (`app.dvp.max-import-record-bytes`). The options part is limited to 64 KiB. `app.dvp.max-concurrent-uploads` defaults to 2 per API instance; account for all replicas. Multipart parsing spools files to the servlet container's temporary directory before they are copied into durable storage, so both locations need enough disk space. Uploads are hashed and fsynced outside a database transaction, atomically published under an opaque server-generated name, and registered with their job and idempotency response in one database transaction. Incomplete uploads are never enqueued. Before processing, each worker verifies the recorded file size and SHA-256 outside a transaction; a bounded per-process cache uses size, modification time and filesystem identity to avoid rehashing unchanged files for every batch. Restrict write access to the import root: that cache is not a defense against an actor who can alter a file while preserving its metadata. Integrity checking reads the full file and adds startup I/O. A mismatch fails the job with `import_file_corrupt`.

Each record applies its document, source texts, provided vectors, counters and checkpoint atomically. JSONL checkpoints retain byte offset and line; JSON checkpoints retain ordinal and reparse on resume. `expected_revision` is an optional positive document revision and a mismatch records `revision_conflict`. For each embedding, provide `indexation_id`, `profile_id`, `text_id`, the SHA-256 `input_hash` of the profile-prepared text, and `values`; `on_conflict` is `keep` by default or `replace`. The text must appear in that record and match a ready, collection-owned index configuration using the declared profile and `chunking.mode=none`. Duplicate indexation/text pairs, mismatched hashes, invalid dimensions or nonfinite values, zero cosine vectors, and incompatible halfvec values fail the entire record. The importer does not call an inference provider or verify the asserted model provenance.

A terminal import file is retained for at least 30 days after the latest terminal job in its retry chain. Failed records can be retried through `/api/v2/jobs/{job_id}/retries`; retry jobs reuse the original file and process failed locators in order. Active descendants protect the file from cleanup. A missing or expired file returns 409 `import_file_unavailable` when requesting a retry. JSON files with a global syntax error require correction and a new upload. Workers periodically remove service-owned expired files and orphaned temporary files after the configured retention periods; locked in-progress files are skipped. Restrict the import root to this service and do not place unrelated files there.

The existing V3/V4 schema is used; no new migration or v1 reindex is required. Before rollback, disable import workers and wait for or stop active uploads, then deploy the earlier application while retaining the schema, job registry, durable files, source data and dynamic vector tables. A full recovery needs a consistent backup of both PostgreSQL and the shared import volume. Do not remove tables, indexes or volumes as an application rollback.

Production-scale verification: no 10 GiB import benchmark or deployment-volume throughput benchmark has been run. Verify capacity and the required filesystem semantics on the actual shared volume before enabling imports.
